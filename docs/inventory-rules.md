# 库存业务规则

本文件是库存及后续单据代码的强制业务基线。当前已经实现库存余额、库存流水、内部库存变更服务、采购入库、销售出库、仓库间调拨和静态盘点闭环。

## 库存字段

- `actual_quantity`：实际库存，物理上仍位于指定实体仓库和库位的数量，包含已冻结但未离仓的数量。
- `frozen_quantity`：已被销售出库或调拨等业务占用、仍在仓内且不能再次分配的数量。
- `available_quantity`：当前可继续分配的数量，等于实际库存减冻结库存。

正常情况下必须长期满足：

```text
actual_quantity = available_quantity + frozen_quantity
actual_quantity >= 0
available_quantity >= 0
frozen_quantity >= 0
frozen_quantity <= actual_quantity
```

当前数据库实际持久化三个数量，并以数据库 `CHECK`、受限条件更新和 Java 不变量对象保证三者关系；可用量不是可任意修改的独立权威值。

## 库存唯一维度

已确认的计划维度：

```text
warehouse_id + location_id + sku_id
```

同一组合只能有一条库存余额，且库位必须属于对应仓库。

## 核心操作变化

设业务数量为 `Q > 0`：

| 操作 | actual | available | frozen |
|---|---:|---:|---:|
| 采购确认入库 | `+Q` | `+Q` | `0` |
| 冻结库存 | `0` | `-Q` | `+Q` |
| 实际出库 | `-Q` | `0` | `-Q` |
| 取消冻结 | `0` | `+Q` | `-Q` |
| 盘盈审核调整 | `+Q` | `+Q` | `0` |
| 盘亏审核调整 | `-Q` | `-Q` | `0` |

盘亏不得导致 `actual < frozen`。若差异超过可用库存，应阻止审核并先处理有效冻结。

## 库存流水

- 采购入库、冻结、释放、实际出库、盘盈盘亏、调拨冻结/释放/出入仓均必须写流水。
- 流水记录仓库、库位、SKU、业务类型、业务单号、业务明细、操作类型、操作人和时间。
- 同时记录实际量及冻结量的前值、变化值和后值；可用量可由二者推导。
- 流水必须满足 `after = before + change`，普通业务接口不得修改或删除。
- 同一业务明细的同一操作只能形成一次流水，计划使用业务动作唯一键保证。

## 幂等要求

- 重复确认采购入库不得重复增加库存。
- 重复提交销售单不得重复冻结。
- 重复取消不得重复释放。
- 重复确认出库不得重复扣减。
- Redis 幂等令牌只能是入口保护；最终依赖单据前置状态、数据库条件更新和唯一约束。

## 并发更新要求

- 禁止“查询可用量 → Java 判断 → 无条件更新”。
- 冻结必须在 MySQL 单条条件更新中包含可用量充足条件，并检查影响行数。
- 释放和出库必须包含冻结量充足条件。
- `version` 可辅助检测丢失更新，但数量条件才是防止超卖的关键。
- 多明细库存操作按稳定顺序访问库存行以降低死锁概率；任一失败整单回滚。

## 事务一致性

一次业务动作中的单据状态、单据明细占用、库存余额、库存流水必须处于同一 MySQL 本地事务。库存事件只能在事务成功后发布，消息失败不得回滚或篡改已提交的库存事实。

## 调拨规则

规则已确认并实现：

- 提交调拨先冻结源仓：可用 `-Q`，冻结 `+Q`。
- 源仓发出：实际 `-Q`、冻结 `-Q`，在途 `+Q`。
- 目标仓收货：目标实际/可用 `+Q`，在途 `-Q`。
- 在途库存单独建模，不计入源仓或目标仓实际库存，不使用虚拟实体仓混入普通库存。
- MVP 后的第一版调拨只考虑整单发出、整单收货。
- 调拨状态为 `DRAFT → SUBMITTED → APPROVED → OUTBOUND_COMPLETED → IN_TRANSIT → COMPLETED`。
- 提交时冻结源库存；`SUBMITTED`、`APPROVED` 可取消并释放，调出后禁止普通取消。
- `stock_transfer_transit` 独立记录调出量、在途量和已收货量；在途量不进入任一仓库余额。

## 盘点规则

规则已确认并实现：采用静态盘点。创建盘点单时在本地事务内按库位、SKU稳定顺序锁定余额行，保存 actual/available/frozen/version 快照并建立持久化维度锁；事务提交后不长期持有数据库行锁。维度锁从创建成功持续到 `ADJUSTED`，期间所有普通库存变更均被条件 SQL 拒绝。

状态固定为 `DRAFT → COUNTING → SUBMITTED → APPROVED → ADJUSTED`。`COUNTING` 录入全部实盘数和原因，差异自动计算为 `counted - snapshot_actual`；只有 `APPROVED` 可调整，同一盘点单只能调整一次。

盘盈将 actual/available 同量增加，盘亏将 actual/available 同量减少，frozen 不变；若实盘数量小于快照冻结量则拒绝调整。调整校验余额版本和三个快照字段，并在同一事务逐行更新余额、写 `INVENTORY_COUNT` 流水、转换状态和释放维度锁。

## 待确认问题

- SKU 是否全部允许四位小数，还是按计量单位限制小数位。
- 销售出库由用户明确选择库位，还是系统自动分配库位。
- 安全库存阈值已经确定为仓库 + 库位 + SKU 唯一维度；消费者始终查询 MySQL 最新 `available_quantity`，严格小于阈值时打开预警，恢复到阈值及以上时解除。
- 库存余额首次创建的并发插入及失败重试策略细节。
- 第二阶段是否需要部分盘点、盘点复核和调拨异常处理。

## 当前库存底座实现（2026-08-14）

- `inventory_balance` 使用 `(warehouse_id, location_id, sku_id)` 唯一约束，三个数量为 `DECIMAL(19,4)`。
- 数据库 `CHECK` 和 Java `InventoryBalanceState` 同时校验非负及 `actual = available + frozen`。
- `inventory_ledger` 分别保存 actual、available、frozen 的前值、变化值和后值，并保存业务类型、业务单号、操作人及版本前后值。
- `InventoryMutationApplicationService` 使用预期 `version` 条件更新并原子递增；影响行数不是 1 时拒绝写流水。
- 余额更新与流水新增使用同一 Spring/MySQL 本地事务。流水 Mapper 不暴露更新或删除方法。
- 对外仅提供余额和流水分页查询，不提供直接设置数量、初始化或手工调整 Controller。
- 当前完成零库存初始化、通用差量变更底座、采购入库、销售冻结/释放/出库、调拨出入库和静态盘点调整。
- 采购入库现已调用库存应用服务执行 `actual +Q`、`available +Q`、`frozen +0`；单据完成、余额更新和流水追加处于同一事务。
- 销售冻结使用 `available_quantity >= Q` 的条件更新，实际出库和释放使用 `frozen_quantity >= Q` 的条件更新；必须检查受影响行数。三个动作分别写 `OUTBOUND_FREEZE`、`OUTBOUND_SHIP`、`OUTBOUND_RELEASE` 流水，并与单据状态更新处于同一事务。
- 销售多明细库存写入固定按 `location_id`、`sku_id` 升序执行，调用方传入顺序不得影响加锁顺序；这降低不同单据竞争相同多维库存时的死锁风险，但数据库死锁仍应作为可观测异常处理，不能宣称理论上绝对不存在。
- 同一销售单的冻结、取消和出库先锁定单据行，因此取消与出库并发时只能有一个动作基于合法状态成功；另一个动作在获得锁后读取最新状态并失败，不能继续修改库存。
- 应用数据库账号或 DBA 直接执行 SQL 仍可修改流水；若生产环境要求数据库级不可变，需要拆分迁移账号与运行账号，并收紧运行账号的 UPDATE/DELETE 权限，当前开发环境尚未实施。

## 实施前置检查

开始库存中心编码前，必须先由用户确认上述待确认项中至少前三项。还需确定：

- 库存余额是否在首次采购入库时惰性创建；
- 可用量采用 MySQL `STORED` 生成列还是查询表达式；
- 库存写服务是否只作为内部应用服务开放，不建立通用写 Controller；
- 流水业务动作键的组成和库存版本链规则；
- 并发测试使用真实 MySQL 集成测试还是 Testcontainers。
