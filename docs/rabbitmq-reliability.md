# RabbitMQ 与业务事件可靠性审查

## 结论与边界

当前实现是“同库事务性 Outbox + RabbitMQ 至少一次投递语义 + 消费者数据库幂等”，不是端到端恰好一次，也不承诺消息绝不丢失或绝不重复。库存余额、冻结、扣减和单据状态转换始终在 MySQL 本地事务中完成；RabbitMQ 只处理完成后的低库存预警等允许延迟的异步副作用。

本文分类含义：

- **当前已经解决**：代码中已有防线，并有自动化测试覆盖对应关键路径。
- **当前通过补偿降低风险**：故障仍可能发生，但有可重试事实、幂等或异常记录降低后果。
- **MVP 明确接受的限制**：当前不继续扩展，但必须诚实保留的风险。
- **后续生产化改进**：上线到更高可靠性环境前建议补齐的能力。

## 逐项审查

| 场景 | 当前状态与实际机制 | MVP 限制 | 后续生产化改进 |
|---|---|---|---|
| 1. 数据库成功但消息未发送 | **当前已经解决主要崩溃窗口**：业务完成事件与库存、流水、单据状态在同一 MySQL 事务写入 Outbox，发布器只扫描已提交记录；进程在提交后、发送前退出时，记录仍可再次扫描。**补偿降低风险**：MQ 不可用时有限重试，8 次失败后转 `FAILED` 并写 `async_failure_record`。 | `FAILED` 不会自动恢复；消息功能关闭时 Outbox 会积压。没有人工重放 API、待发布时长告警和当班处理闭环。 | 增加 Outbox 最老年龄/失败数监控、授权重放 API、操作审计、处置手册与保留/归档策略；按实际故障时长调整重试，而不是固定较短窗口。 |
| 2. 消息发送成功但数据库回滚 | **当前已经解决“业务事务回滚却发送成功事件”**：业务事务内只写 Outbox，不连接 MQ，回滚会一并撤销 Outbox。发布器只能看到已提交行。 | Broker 已确认后，发布器更新 Outbox 状态的数据库事务仍可能失败；该行会再次发布，因此可能重复，但不会把核心库存事务回滚。 | 保持至少一次语义并强化消费幂等；增加发布租约/占用超时和重复率指标。除非有强制需求，不引入 XA/分布式事务。 |
| 3. 消息重复投递 | **当前已经解决同一消息 ID 对低库存副作用的重复执行**：`message_id + consumer_name` 唯一约束，幂等占位与预警变更在同一事务；重复消息只记录重复轨迹。 | 同一业务事实若错误地产生两个不同消息 ID，不属于当前通用幂等键覆盖范围；当前预警按最新库存状态更新，不能据此声称所有未来消费者都天然幂等。 | 为每类新消费者明确业务幂等键；必要时增加稳定业务事件键和唯一约束，并做重复率告警。 |
| 4. 消费成功但 ACK 失败 | **当前通过幂等补偿降低风险**：监听方法事务提交后才返回；ACK 丢失会引起再次投递，同一消息 ID 被消费记录拦截。 | 这是允许重复的至少一次处理，不是恰好一次；RabbitMQ 与 MySQL 之间没有原子 ACK 事务。 | 监控 redelivered/重复消费比例；继续要求所有新消费者把幂等占位与数据库副作用放入同一事务。 |
| 5. 消费者执行一半后异常 | **当前已经解决现有数据库副作用的半提交**：消费幂等占位、同批预警打开/解除和轨迹在同一 MySQL 事务，异常整体回滚，随后可用同一消息重试。真实 MySQL 回归覆盖了“首个维度已处理、后续维度失败”的场景。 | 如果以后直接调用邮件、短信或第三方 HTTP，这些外部副作用不受当前数据库事务保护。 | 外部通知使用独立通知 Outbox，并以消息 ID/通知目标作为幂等键；不得在现有事务中直接假定第三方调用可回滚。 |
| 6. 重试造成重复业务操作 | **当前已经解决现有低库存处理的同消息重复操作**：最多 3 次消费尝试，失败继续抛出；数据库事务回滚后重试，提交成功后的重复由唯一幂等键吸收。 | 只保证当前低库存消费者；未来统计累加、外部通知若没有独立幂等设计仍会重复。 | 对统计改为可重算或按事件唯一键去重；对外部通知保存发送意图和结果，加入契约级幂等测试。 |
| 7. 死信无人处理 | **当前通过补偿降低风险**：永久失败经发布确认后进入持久死信队列，死信消费者把原始载荷、原因、次数和补偿状态写入 `async_failure_record`。本轮修复了死信重发未等待确认的问题；若死信交换机不可用，原消息会重新入队而不是静默丢弃。 | 异常记录仍可能长期无人处理；没有管理页面/API、告警、SLA 或自动重放。单节点 Broker/单磁盘也不是高可用。 | 建立失败记录告警、责任人、处置时限、授权重放/忽略流程和审计；根据部署要求使用 RabbitMQ 集群与 quorum queue，并验证灾备恢复。 |
| 8. 消息格式升级导致旧消费者失败 | **当前已经解决“旧消费者误按新格式处理”**：信封包含 `eventName`、`eventVersion`，v1 使用版本化交换机/路由；编解码器拒绝未知版本，失败经有限重试后进入异常记录，旧业务处理器不会被调用。 | 当前只支持 v1，没有兼容矩阵、Schema Registry、双版本灰度消费或跨版本契约测试。拒绝新版本是安全失败，不是向前兼容。 | 优先做可加字段演进；破坏性变更使用 v2 路由/队列和并行消费者，完成灰度后退役 v1；增加生产者—消费者契约测试和 Schema 管理。 |
| 9. MQ 长时间不可用 | **当前通过 Outbox 补偿降低风险**：核心入出库业务仍可提交，待发事实保存在 MySQL；发布有上限和退避，终止后保留失败记录。 | 8 次上限后不会自动恢复；没有 outage-aware 暂停、自动重放、容量保护或故障时长 SLO。长时间故障会转化为 Outbox/异常记录积压。 | 增加连接状态熔断、按故障窗口设计的重试/重放任务、Outbox 容量与年龄告警、恢复后限速追赶及演练。 |
| 10. 消息堆积 | **当前只有基础保护**：发布器每批 20 条、固定 2 秒调度，并用 `FOR UPDATE SKIP LOCKED`；消费者并发为 1；毒消息最多 3 次后移出主队列，避免单条无限阻塞。 | 没有吞吐/延迟压测，不能给出 TPS、清空时间或容量承诺；没有队列深度、最老消息年龄、消费速率监控，也没有自动扩缩容、背压或历史清理。 | 建立 Outbox 与 RabbitMQ 指标和告警；基于幂等与数据库容量压测后调整批量、调度和消费者并发；增加保留/归档、流控和恢复追赶方案。 |

## 本轮修复

1. 普通 `RepublishMessageRecoverer` 改为带 publisher confirm 的 `RepublishMessageRecovererWithConfirms`。只有死信发布得到确认，原消息才结束恢复流程；死信发布失败时抛出异常并重新入队。
2. RabbitMQ Compose 增加固定 hostname 和 `/var/lib/rabbitmq` 命名卷，降低容器重建导致本地 Broker 数据直接消失的风险。该配置不等同于节点、磁盘或机房高可用。
3. 新增回归测试覆盖消费者中途失败事务回滚后同消息可重试、死信交换机不可用时原消息不会被静默丢弃，以及 v2 消息不会调用 v1 消费者而会留下异常记录。

## 未被改变的设计

- 不把库存最终扣减、冻结、入库或单据状态交给 RabbitMQ。
- 不使用 `@TransactionalEventListener(AFTER_COMMIT)` 作为唯一投递保证；当前选择简化 Outbox，保留提交后的可恢复发送事实。
- 不承诺 RabbitMQ 天然保证绝不丢失、绝不重复或端到端恰好一次。
