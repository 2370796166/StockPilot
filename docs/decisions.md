### DEC-001 采用模块化单体

- 状态：已确认

### DEC-003 MySQL 是库存唯一权威来源

- 状态：已确认
- 背景：库存必须在缓存或消息系统异常时仍保持正确。
- 最终选择：库存余额、条件判断和最终约束以 MySQL 为准。
- 选择原因：MySQL 原子条件更新、本地事务和唯一约束的故障模型更清晰。
- 被放弃的方案：Redis 库存为主、Redis 分布式锁决定超卖、MQ 异步扣库存。
- 影响：库存写入、单据状态和流水必须在本地事务中完成。

### DEC-004 Redis 只承担辅助能力

- 状态：已确认
- 背景：项目需要 Redis 的真实场景，但不能影响库存权威性。
- 最终选择：Redis 仅用于缓存、JWT 辅助、短期限流或入口幂等。
- 选择原因：这些数据可失效或重建，不承担库存最终一致性。
- 被放弃的方案：Redis 保存权威库存、仅靠 Redis 幂等保护重复扣减。
- 影响：Redis 故障不能导致库存错误；数据库仍需最终幂等防线。
- 日期：2026-08-13

### DEC-005 RabbitMQ 只用于真实异步业务

- 状态：已确认
- 背景：安全库存预警允许延迟，库存扣减不允许依赖异步成功。
- 最终选择：RabbitMQ 用于库存变化后的预警等异步任务，采用至少一次投递思路和消费端幂等。
- 选择原因：异步解耦有实际价值，核心事务不受消费者故障影响。
- 被放弃的方案：为展示技术而发送无业务意义消息、通过 MQ 完成核心扣减。
- 影响：消费者查询 MySQL 最新库存；后续阶段已选择简化事务性 Outbox，RabbitMQ 不参与库存最终扣减。
- 日期：2026-08-13

### DEC-013 基础资料更新使用乐观锁

- 状态：已确认
- 背景：基础资料可能被多个管理用户同时修改，直接覆盖会造成丢失更新。
- 最终选择：表保存 `version`，Entity 使用 MyBatis-Plus `@Version`，修改和状态变更必须提交当前版本；影响行数不为 1 时返回 409。

### DEC-014 当前JWT采用无Redis的HS256实现

### DEC-016 库存底座采用三数量持久化与追加式流水

- 状态：已确认
- 背景：库存底座需要支持后续入库、冻结、释放和出库，同时长期保持数量正确和可审计。
- 最终选择：余额按仓库、库位、SKU 唯一，actual、available、frozen 使用 `DECIMAL(19,4)` 持久化；Java 和 MySQL 双重校验不变量。差量变更使用预期版本条件更新并在同一事务新增完整流水。
- 选择原因：三个数量语义直观，条件更新可检测并发冲突，前值/变化值/后值与版本链可独立复核。
- 被放弃的方案：只在 Java 先查后改、直接设置余额的 CRUD、仅记录单一总量变化、通过 Redis 锁决定库存正确性。
- 影响：库存 Controller 仅提供查询；流水 Mapper 仅新增和查询；采购、销售等模块只能调用库存应用服务，不能调用库存 Mapper。
- 日期：2026-08-14

### DEC-017 采购入库采用四状态闭环与单据行锁

- 状态：已确认并实现
- 背景：采购入库必须保证同一单据只生效一次，并让单据、库存余额和流水保持原子一致。
- 最终选择：状态固定为 `DRAFT → SUBMITTED → APPROVED → COMPLETED`，当前不增加没有后续处理闭环的 `REJECTED`、`CANCELLED`。完成入口使用 `SELECT ... FOR UPDATE` 锁定单据，逐明细调用库存应用服务，最后条件更新为 `COMPLETED`。
- 权限：读取、写入/提交、审核、执行入库分别使用 `PURCHASE_RECEIPT_READ`、`PURCHASE_RECEIPT_WRITE`、`PURCHASE_RECEIPT_APPROVE`、`PURCHASE_RECEIPT_COMPLETE`。
- 职责分离：当前不额外校验制单人 ID 与审核人 ID 不同；默认 `OPERATOR` 与 `AUDITOR` 权限已分离，`ADMIN` 保留全流程能力。
- 幂等：单号唯一、单据状态、单据行锁、明细维度唯一和库存流水业务动作唯一键共同保证；Redis 不参与最终正确性。
- 事务：执行入库的基础资料复核、余额变更、流水新增和单据完成处于同一 MySQL 本地事务，任一步失败全部回滚。
- 日期：2026-08-14

### DEC-018 销售出库采用原子条件更新和五状态闭环

- 状态：已确认并实现
- 状态机：`DRAFT → RESERVED → APPROVED → COMPLETED`；只有已冻结但未出库的 `RESERVED`、`APPROVED` 可转为 `CANCELLED`。不增加没有实际处理语义的 `SUBMITTED` 或 `REJECTED`。
- 并发：单据动作先用 `SELECT ... FOR UPDATE` 锁定单据；不同单据竞争同一库存时，以 MySQL 原子条件更新为准。冻结要求 `available_quantity >= Q`，出库要求 `actual_quantity >= Q AND frozen_quantity >= Q`，释放要求 `frozen_quantity >= Q`，并检查受影响行数。
- 错误转换：条件更新影响零行时，余额不存在映射为余额不存在；余额存在则分别映射为可用库存不足或冻结库存不足，不重试无条件更新。
- 事务：冻结、实际出库、取消释放各自是独立本地事务边界；每个事务同时更新库存余额、追加对应类型的不可变流水并更新单据状态，任一步失败全部回滚。
- 幂等：状态机和单据行锁提供入口防重；业务单号唯一、明细维度唯一和流水 `(business_type, business_no, warehouse_id, location_id, sku_id)` 唯一约束作为最终保障。
- 基础资料：创建、编辑和冻结时要求仓库、库位、SKU 存在且启用；冻结后即使基础资料随后停用，也允许完成出库或取消释放，避免冻结库存无法闭环。
- 权限：`SALES_OUTBOUND_READ`、`SALES_OUTBOUND_WRITE`、`SALES_OUTBOUND_APPROVE`、`SALES_OUTBOUND_COMPLETE`；默认 `OPERATOR` 负责制单、冻结、取消和执行，`AUDITOR` 负责审核，`ADMIN` 保留全流程能力。
- 日期：2026-08-14

### DEC-019 仓库间调拨采用独立在途事实和分段本地事务

- 状态：已确认并实现
- 状态机：`DRAFT → SUBMITTED → APPROVED → OUTBOUND_COMPLETED → IN_TRANSIT → COMPLETED`；`SUBMITTED`、`APPROVED` 可取消并释放源仓冻结，调出后禁止普通取消。
- 库存：提交原子冻结源库存；调出扣减源实际量和冻结量；目标收货增加目标实际量和可用量。
- 在途：使用 `stock_transfer_transit` 独立保存调出、在途和已收货数量，不建立虚拟仓，也不让在途同时计入源仓或目标仓实际库存。
- 事务：提交、调出、调入分别使用单体单 MySQL 本地事务。每个动作内的单据状态、全部明细库存、流水和在途记录共同提交或回滚。
- 幂等：单据行锁、前置状态、条件更新、调拨单号/明细/在途唯一约束和库存流水业务动作唯一键共同保证。
- 明细：同单源库位/SKU与目标库位/SKU分别唯一，避免一个流水业务动作键对应多个调拨明细。
- 并发：源端按源库位、SKU、目标库位排序；目标端按目标库位、SKU、源库位排序。
- 日期：2026-08-14

### DEC-020 库存盘点采用维度级静态冻结

- 状态：已确认并实现
- 状态机：`DRAFT → COUNTING → SUBMITTED → APPROVED → ADJUSTED`；未审核不能调整，`ADJUSTED` 不能再次调整。
- 快照与限制：创建时按库位、SKU稳定顺序锁定库存余额，保存 actual、available、frozen 和 version 快照，并建立 `(warehouse_id, location_id, sku_id)` 唯一维度锁。锁存在期间，采购、销售、调拨及通用库存变更均不得修改该维度。
- 调整：差异为实盘量减快照实际量。盘盈/盘亏同量改变 actual 与 available，frozen 不变；实盘量小于 frozen 时拒绝调整。
- 事务：创建的快照与维度锁处于一个本地事务；调整时单据行锁、全部余额变更、盘点流水、状态转换和锁释放处于另一个本地事务，任一失败全部回滚。
- 幂等与并发：状态机、单据行锁、维度锁唯一键、快照版本/三字段条件更新和库存流水业务动作唯一键共同保证；不引入 Redis 锁或分布式事务。
- 流水：`INVENTORY_COUNT` 流水额外保存盘点单号、账面实际量、实盘量、差异和原因，包括无差异调整。
- 日期：2026-08-14

### DEC-021 Redis首批只缓存SKU和仓库单键详情

- 状态：已确认并实现
- 查询审计：SKU、仓库详情是读多写少的单键查询，适合 Cache Aside；分页基础资料组合键多、失效范围大，库存余额和流水变化频繁且当前没有独立热点摘要接口，因此暂不缓存。
- Key与格式：`stockpilot:v1:master:sku:id:{id}`、`stockpilot:v1:master:warehouse:id:{id}`；值为 UTF-8 JSON 版本信封，保存 `schemaVersion=1`、是否存在和对应 VO。Key 前缀与信封双重标识格式版本，未知版本按未命中处理。
- TTL与穿透：SKU和仓库正常详情均为30分钟；不存在数据写入 `found=false` 空值60秒。当前没有单Key热点证据，不实现分布式锁、复杂双删或击穿重建协调。
- 一致性：读请求先查Redis，未命中查MySQL并回填；创建、更新、启停在MySQL成功后删除对应Key。Redis删除失败不回滚数据库，缓存最多在TTL窗口内陈旧；业务写流程的基础资料有效性校验继续直查MySQL。
- 派生字段：SKU缓存不保存可复用的分类名称；命中后按`categoryId`从MySQL补齐当前分类名称，避免分类独立更新使SKU详情中的派生名称陈旧。未引入Key扫描或分类到SKU的反向集合。
- 降级与边界：缓存通过 `CACHE_ENABLED` 开关控制，默认关闭；Redis连接、读取、写入、删除或反序列化失败均降级MySQL。Redis不缓存库存余额，不参与库存扣减、库存事务、JWT、密码或最终幂等。
- 日期：2026-08-18

### DEC-022 入出库完成事件采用简化事务性 Outbox

- 状态：已确认并实现
- 事件契约：`stockpilot.purchase-receipt.completed` v1 与 `stockpilot.sales-outbound.completed` v1；每条消息使用 UUID 唯一 ID，并携带业务单号、发生时间、单据 ID、仓库 ID 和受影响的库位/SKU 维度，不传完整数据库实体。
- 事务关系：入库或出库完成时，在库存余额、流水和单据状态所在的同一 MySQL 事务写 Outbox；事务提交前不连接 RabbitMQ，回滚会同时删除 Outbox 成功事件。调度器只处理已提交记录。
- 选择原因：`@TransactionalEventListener(AFTER_COMMIT)` 可避免提交前发送，但应用在提交后、实际发送前崩溃时没有可恢复事实；简化 Outbox 能在 MQ 不可用时保留待发布记录。
- 发布可靠性：消息持久化并启用 mandatory、publisher confirm/return；收到 ack 且未 return 后才标记 `PUBLISHED`。发布最多尝试 8 次，达到上限写 `async_failure_record`。Broker ack 后应用在数据库提交前崩溃仍可能重复发布，因此不承诺绝不丢失或绝不重复。
- 消费可靠性：消费者最多尝试 3 次，异常必须继续抛出；永久失败由带 publisher confirm 的 recoverer 投递到持久死信交换机/队列，确认失败时原消息重新入队，确认成功后由死信消费者落异常记录。消费幂等键为消息 ID + 消费者名，并与预警变更处于同一本地事务。
- 业务边界：RabbitMQ 不执行库存冻结、扣减、入库或单据状态转换。安全库存消费者只查询 MySQL 最新可用量，并按仓库 + 库位 + SKU 创建、更新或解除预警。
- 运维审计：`async_message_trace` 保存关键阶段；`async_failure_record` 保存原始载荷、失败原因、次数、补偿状态、处理人和备注。Compose 为 RabbitMQ 数据目录配置命名卷，但单节点持久化不等同于高可用。当前未开放人工补偿 HTTP API。
