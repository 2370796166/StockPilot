# 技术决策记录

### DEC-001 采用模块化单体

- 状态：已确认
- 背景：项目由本科生开发，需要完整业务闭环且复杂度可控。
- 最终选择：单一 Spring Boot 部署单元，按业务能力划分包/模块。
- 选择原因：保留清晰边界和本地事务，同时降低部署、调试和学习成本。
- 被放弃的方案：Spring Cloud 微服务、Kubernetes、分布式事务。
- 影响：跨模块通过公开应用服务协作，禁止跨模块调用 Mapper。
- 日期：2026-08-13

### DEC-002 后端优先

- 状态：已确认
- 背景：项目核心价值在库存业务正确性，开发者正在准备 Java 实习。
- 最终选择：先完成后端核心流程、测试和文档，再开发 Vue 3 前端。
- 选择原因：优先投入事务、并发、幂等和数据库设计。
- 被放弃的方案：前后端同时铺开或先做展示页面。
- 影响：当前和下一阶段不开发前端。
- 日期：2026-08-13

### DEC-003 MySQL 是库存唯一权威来源

- 状态：已确认
- 背景：库存必须在缓存或消息系统异常时仍保持正确。
- 最终选择：库存余额、条件判断和最终约束以 MySQL 为准。
- 选择原因：MySQL 原子条件更新、本地事务和唯一约束的故障模型更清晰。
- 被放弃的方案：Redis 库存为主、Redis 分布式锁决定超卖、MQ 异步扣库存。
- 影响：库存写入、单据状态和流水必须在本地事务中完成。
- 日期：2026-08-13

### DEC-004 Redis 只承担辅助能力

- 状态：已确认
- 背景：项目需要 Redis 的真实场景，但不能影响库存权威性。
- 最终选择：Redis 仅用于缓存、JWT 辅助、短期限流或入口幂等。
- 选择原因：这些数据可失效或重建，不承担库存最终一致性。
- 被放弃的方案：Redis 保存权威库存、仅靠 Redis 幂等保护重复扣减。
- 影响：Redis 故障不能导致库存错误；数据库仍需最终幂等防线。
- 日期：2026-08-13

### DEC-005 RabbitMQ 只用于真实异步业务

- 状态：已确认
- 背景：安全库存预警允许延迟，库存扣减不允许依赖异步成功。
- 最终选择：RabbitMQ 用于库存变化后的预警等异步任务，采用至少一次投递思路和消费端幂等。
- 选择原因：异步解耦有实际价值，核心事务不受消费者故障影响。
- 被放弃的方案：为展示技术而发送无业务意义消息、通过 MQ 完成核心扣减。
- 影响：消费者查询 MySQL 最新库存；生产可靠性后续再评估 Outbox。
- 日期：2026-08-13

### DEC-006 先核心业务，后接入 Redis 和 RabbitMQ

- 状态：已确认
- 背景：过早接入中间件会掩盖库存模型和事务问题。
- 最终选择：先完成基础资料及核心库存/单据正确性，再接入 Redis 和 RabbitMQ。
- 选择原因：保证每项技术都有可解释的业务边界。
- 被放弃的方案：项目骨架阶段一次性加入全部技术栈。
- 影响：认证已在后续获得用户授权后完成；当前仍禁止在核心库存业务完成前接入 Redis 和 RabbitMQ。
- 当前状态说明：认证已在用户明确指定的后续阶段完成；Redis、RabbitMQ 仍需等待核心库存业务正确后接入。
- 日期：2026-08-13

### DEC-011 无状态 Access Token 与数据库实时授权

- 状态：已确认
- 最终选择：仅实现 JWT Access Token；令牌只保存用户身份和有效期，每次请求从 MySQL 加载用户状态与权限。
- 选择原因：停用用户和授权调整立即生效，无需 Redis 登录状态、黑名单或复杂 Refresh Token。
- 安全约束：密码使用 BCrypt；JWT 密钥由环境变量提供；审计摘要使用白名单字段，不记录密码或完整 Token。
- 日期：2026-08-13

### DEC-012 安全接口双层授权与独立授权权限

- 状态：已确认
- 最终选择：安全与基础资料接口同时使用 URL 白名单权限和方法级 `@PreAuthorize`；未列入规则的新接口默认拒绝。用户角色和角色权限变更使用独立 `SECURITY_GRANT` 权限，仅预置给系统管理员。
- 选择原因：防止新增接口漏写方法权限，也防止仅持有普通用户/角色写权限的账号通过修改授权关系实现垂直提权。
- 日期：2026-08-13

### DEC-013 基础资料更新使用乐观锁

- 状态：已确认
- 背景：基础资料可能被多个管理用户同时修改，直接覆盖会造成丢失更新。
- 最终选择：表保存 `version`，Entity 使用 MyBatis-Plus `@Version`，修改和状态变更必须提交当前版本；影响行数不为 1 时返回 409。
- 选择原因：实现成本低，适合读多写少的基础资料。
- 被放弃的方案：悲观锁、最后写入覆盖前一次修改。
- 影响：前端或调用者修改前必须先获取最新 VO 中的 `version`。
- 日期：2026-08-13

### DEC-014 当前JWT采用无Redis的HS256实现

- 状态：已确认（当前阶段）
- 背景：需要先完成可解释的登录和接口权限，又不应提前引入 Redis。
- 最终选择：使用外部环境提供的至少 32 字符密钥签发 HS256 Access Token，每次请求从 MySQL 重载用户和权限。
- 选择原因：无服务端会话，停用和授权变化可立即生效，基础复杂度可控。
- 被放弃的方案：Refresh Token、Redis 黑名单、OAuth2/SSO、在 Token 中固化权限。
- 影响：单个 Token 暂时无法主动撤销；安全密钥缺失时不能签发或验证 Token。
- 日期：2026-08-13

### DEC-015 最终MVP采用三个逻辑角色

- 状态：已确认
- 背景：最终 MVP 为控制实习项目复杂度，只需要管理员、业务员和审核员；早期 `V0.3.0` 曾预置六个细分角色。
- 最终选择：产品需求和默认种子统一为 `ADMIN`、`OPERATOR`、`AUDITOR` 三个逻辑角色，通过新增 `V0.3.2` 迁移收敛已有数据，不修改已执行的历史迁移。
- 选择原因：三角色足以演示 RBAC、职责分离和核心库存流程，能避免权限矩阵在业务尚未实现前过度扩张。
- 被放弃的方案：把采购、销售、仓库、只读等六种角色作为最终 MVP 强制需求。
- 影响：`SYSTEM_ADMIN` 用户关系迁移到 `ADMIN`；早期仓库、采购、出库和只读角色迁移到 `OPERATOR`；`AUDITOR` 保留。`ADMIN` 拥有现有全部权限，`OPERATOR` 仅有基础资料读取，`AUDITOR` 有基础资料和审计读取。后续新增库存、采购和销售权限时继续围绕三角色设计。
- 日期：2026-08-14

### DEC-016 库存底座采用三数量持久化与追加式流水

- 状态：已确认
- 背景：库存底座需要支持后续入库、冻结、释放和出库，同时长期保持数量正确和可审计。
- 最终选择：余额按仓库、库位、SKU 唯一，actual、available、frozen 使用 `DECIMAL(19,4)` 持久化；Java 和 MySQL 双重校验不变量。差量变更使用预期版本条件更新并在同一事务新增完整流水。
- 选择原因：三个数量语义直观，条件更新可检测并发冲突，前值/变化值/后值与版本链可独立复核。
- 被放弃的方案：只在 Java 先查后改、直接设置余额的 CRUD、仅记录单一总量变化、通过 Redis 锁决定库存正确性。
- 影响：库存 Controller 仅提供查询；流水 Mapper 仅新增和查询；采购、销售等模块只能调用库存应用服务，不能调用库存 Mapper。
- 日期：2026-08-14

### DEC-017 采购入库采用四状态闭环与单据行锁

- 状态：已确认并实现
- 背景：采购入库必须保证同一单据只生效一次，并让单据、库存余额和流水保持原子一致。
- 最终选择：状态固定为 `DRAFT → SUBMITTED → APPROVED → COMPLETED`，当前不增加没有后续处理闭环的 `REJECTED`、`CANCELLED`。完成入口使用 `SELECT ... FOR UPDATE` 锁定单据，逐明细调用库存应用服务，最后条件更新为 `COMPLETED`。
- 权限：读取、写入/提交、审核、执行入库分别使用 `PURCHASE_RECEIPT_READ`、`PURCHASE_RECEIPT_WRITE`、`PURCHASE_RECEIPT_APPROVE`、`PURCHASE_RECEIPT_COMPLETE`。
- 职责分离：当前不额外校验制单人 ID 与审核人 ID 不同；默认 `OPERATOR` 与 `AUDITOR` 权限已分离，`ADMIN` 保留全流程能力。
- 幂等：单号唯一、单据状态、单据行锁、明细维度唯一和库存流水业务动作唯一键共同保证；Redis 不参与最终正确性。
- 事务：执行入库的基础资料复核、余额变更、流水新增和单据完成处于同一 MySQL 本地事务，任一步失败全部回滚。
- 日期：2026-08-14
